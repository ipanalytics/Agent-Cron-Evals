## Обзор

Я мониторю задания по расписанию, чтобы обнаруживать сбои до того, как они станут проблемами. Мой подход детерминированный: без модели, без дашборда, без оценок. Я проверяю, что задания запускались достаточно давно, сообщили об успехе, доставили свой вывод и что сторожевые процессы всё ещё живы.

Здоровый запуск ничего не печатает. Проблемы появляются в виде одной строки на каждую, с полными записями, которые всегда записываются на диск.

## Архитектура

Мои проверки работают без модели или сетевого подключения. Архитектура проста:

1. **Свежесть заданий**: Задание запускалось ли достаточно недавно?
2. **Проверка статуса**: Сообщило ли оно об успехе?
3. **Подтверждение доставки**: Дошёл ли вывод?
4. **Отслеживание серий**: Есть ли последовательные сбои?
5. **Мониторинг сторожевых функций**: Сторожевые процессы всё ещё отмечаются?

Этот дизайн обеспечивает надёжность без внешних зависимостей.

## Особенности

- **Молчу при здоровье**: Ничего не печатаю, когда все проверки пройдены
- **Детерминированные проверки**: Арифметика по времени, без вероятностной оценки
- **Настраиваемые пределы**: Установка порогов возраста и серий сбоев
- **Обнаружение ошибок доставки**: Отдельно флаги доставки от статуса задания
- **Мониторинг файлов состояния**: Отслеживаю внешние процессы через файлы времени
- **Логика пропусков**: Учитываю окна расписания и дни недели
- **Исключение самонаблюдения**: Предотвращаю, чтобы мониторы сообщали о собственных сбоях

## Быстрый старт

```sh
pip install git+https://github.com/ipanalytics/Agent-Cron-Evals
cp examples/checks.example.json ~/.hermes/cron-evals.json
agent-cron-evals --config ~/.hermes/cron-evals.json
```

Когда все проверки пройдены, вывод пуст. Когда есть проблемы:

```
утренний дайджест: последний запуск 31.4 ч назад, лимит 27.0 ч
наблюдатель результатов: last_status = error (соединение закрыто без получения полного сообщения)
автозагрузка списка наблюдения: не отмечался 4.2 ч (ожидается каждые 3.5 ч)
счета: 3 сбоя подряд
```

## Использование

### Интерфейс командной строки

```sh
agent-cron-evals --config evals.json                 # только проблемы (для крона)
agent-cron-evals --config evals.json --all           # все проверки плюс сводка
agent-cron-evals --config evals.json --json          # полная запись в JSON
agent-cron-evals --config evals.json --quiet         # записать запись, ничего не печатать
agent-cron-evals --config evals.json --jobs other.json --output /tmp/evals.json
```

### Коды возврата

- `0`: Проверки успешно запущены (проблемы указаны в выводе)
- `2`: Не удалось прочитать конфигурацию или список заданий

### Пример шаблона крона

Я спроектирован для шаблона крона без модели:

```json
{
  "id": "cron-evals",
  "schedule": "0 * * * *",
  "script": "agent-cron-evals --config ~/.hermes/cron-evals.json",
  "no_agent": true,
  "deliver": "telegram:-1000000000000:42"
}
```

Поле `no_agent: true` гарантирует, что stdout доставляется дословно. Пустой stdout ничего не отправляет.

## Справочник проверок

| Название проверки | Что проверяет | Срабатывает когда | Результат/Пропуск |
|-------------------|---------------|-------------------|-------------------|
| Существование задания | Задание в файле расписания | ID задания не найден | FAIL: "missing" |
| Задание включено | Задание включено | `enabled: false` | SKIP: "disabled" |
| Окно расписания | Внутри настроенных часов | Вне окна `hours` | SKIP: "outside its window" |
| Проверка дня недели | Сегодня разрешённый день | Не в списке `days` | SKIP: "not scheduled today" |
| Свежесть | Недавний запуск в пределах лимита | Возраст > `max_age_seconds` | FAIL: возраст превышен |
| Проверка статуса | Статус успеха | `last_status` ≠ `require_status` | FAIL: несоответствие статуса |
| Ошибки доставки | Нет проблем с доставкой | Существует `last_delivery_error` | FAIL: доставка не удалась |
| Серии сбоев | Не в серии | `failure_streak` ≥ `streak_limit` | FAIL: последовательные сбои |
| Файлы состояния | Внешние процессы живы | Время > `max_age_seconds` | FAIL: процесс устарел |

## Конфигурация

Конфигурация использует JSON-файл с этими ключами:

| Ключ | Тип | Описание | По умолчанию |
|------|-----|-----------|--------------|
| `jobs_file` | строка | Путь к файлу расписания заданий | `"~/.hermes/cron/jobs.json"` |
| `output` | строка | Куда записывать JSON-запись | `"~/.hermes/data/cron_evals.json"` |
| `delivery` | булево | Проверять ошибки доставки | `true` |
| `streak_limit` | целое | Сбои подряд для отчёта | `3` |
| `self_monitors` | массив | ID заданий для исключения из проверки серий | `[]` |
| `checks` | массив | Проверки для конкретных заданий | `[]` |
| `state_files` | массив | Мониторы внешних файлов состояния | `[]` |

Пример конфигурации:

```json
{
  "jobs_file": "~/.hermes/cron/jobs.json",
  "output": "~/.hermes/data/cron_evals.json",
  "delivery": true,
  "streak_limit": 3,
  "self_monitors": ["8eafdf0f26f9"],
  "checks": [
    {"job": "a372f46fdbd6", "name": "oura snapshot", "max_age_seconds": 97200},
    {"job": "e70f41682aea", "name": "midday digest", "max_age_seconds": 97200, "days": [0, 1, 2, 3, 4]}
  ],
  "state_files": [
    {"name": "watchlist autofetch", "path": "~/.hermes/data/watchlist_state.json",
     "key": "last_check", "max_age_seconds": 12600}
  ]
}
```

## Выходы/Артефакты

Я записываю JSON-запись в настроенный путь вывода с этими полями:

- `findings`: Массив отдельных результатов проверок
- `problems`: Массив описаний проблем
- `skipped`: Количество пропущенных проверок
- `failed`: Количество неудачных проверок
- `timestamp`: Когда запускалась оценка

Каждая находка содержит:
- `job`: ID задания
- `name`: Человекочитаемое имя
- `state`: `ok`, `fail` или `skip`
- `detail`: Дополнительная информация для пропусков
- `age_seconds`: Возраст последнего запуска задания
- `problems`: Массив строк проблем

## Эксплуатационные замечания

- **Интеграция с кроном**: Спроектирован для запуска каждый час без агента
- **Ночные проверки**: Задание, запланированное на ночь, может показаться нездоровым во время дневных проверок - это ожидаемое поведение, а не ошибка
- **Повреждённые файлы**: Я никогда не выхожу с ошибкой при отсутствии или нечитаемости файлов - повреждённый файл состояния становится находкой, а не трассировкой
- **Тихие сбои**: Я приоритизирую сообщение о проблемах над выходом из строя

## Область применения

Я проверяю здоровье заданий по расписанию через детерминированные проверки. Я не:
- Являюсь планировщиком
- Изменяю файлы заданий
- Предоставляю дашборд
- Оцениваю качество вывода заданий
- Требую сетевого подключения

## Сценарии использования

- Мониторинг запланированных агентов в продакшене
- Обеспечение доставки автоматических отчётов
- Отслеживание надёжности крон-заданий
- Обнаружение тихих сбоев
- Проверка живости сторожевых процессов

## Ограничения

- Только проверяю метаданные заданий (временные метки, статус), а не качество вывода
- Требует правильно форматированных файлов заданий с временными метками
- Ограничен планировщиком крон в стиле Unix
- Без встроенной визуализации, кроме текстового вывода
- Не пытается перезапустить неудачные задания
