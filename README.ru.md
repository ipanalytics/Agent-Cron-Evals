# Agent Cron Evals

_English version: [README.md](README.md)_

**Скажет, какие задачи по расписанию мертвы, — и промолчит, если мертвых нет.**

Работа агента по расписанию — та часть, за которой никто не следит. Задача, которая падает
громко, — это неудобство; задача, которая падает **тихо**, — дыра в системе, потому что
единственное, что могло бы о ней сообщить, это она сама.

Этот пакет заменяет вопрос «а кроны вообще ходили?» детерминированными проверками: без модели,
без дашборда, без баллов. Четыре вопроса:

1. **Задача запускалась, достаточно свежо, и сказала, что всё хорошо?**
2. **Её вывод действительно дошёл?** Ошибка доставки — это провал, даже если задача «успешна».
3. **Не идёт ли по какой-то задаче серия провалов?** Три подряд — уже не случайность.
4. **Сторожевые процессы ещё отмечаются?** Сторож пишет метку времени; старая метка значит,
   что сторож умер тихо.

Здоровый прогон печатает **ничего**. В этом весь интерфейс: молчание — норма, одна строка на
проблему, а полный отчёт всегда пишется на диск.

## Быстрый старт

```sh
pip install git+https://github.com/ipanalytics/Agent-Cron-Evals
cp examples/checks.example.json ~/.hermes/cron-evals.json   # впишите свои id задач
agent-cron-evals --config ~/.hermes/cron-evals.json
```

Когда всё в порядке, вывод пустой. Когда нет — примерно так:

```
morning digest: last run 31.4 h ago, limit 27.0 h
results watcher: last_status = error (peer closed connection without sending complete message body)
watchlist autofetch: has not checked in for 4.2 h (expected every 3.5 h)
invoices: 3 failures in a row
```

## Шаблон «крон без модели»

Инструмент сделан так, чтобы запускаться из крона **без агента и без модели**: текст уходит
прямо в сообщение, поэтому здоровый прогон не должен порождать сообщение вообще.

```json
{
  "id": "cron-evals",
  "schedule": "0 * * * *",
  "script": "agent-cron-evals --config ~/.hermes/cron-evals.json",
  "no_agent": true,
  "deliver": "telegram:-1000000000000:42"
}
```

Поле `no_agent: true` здесь главное: stdout доставляется дословно, пустой stdout не отправляет
ничего. Запускать раз в час безопасно по двум причинам: инструмент никогда не пишет в файл
задач и никогда не падает на отсутствующем файле — битый файл состояния становится находкой, а
не трассировкой.

## Файл конфигурации

Один JSON-объект. Всё, кроме `checks`, необязательно; значения по умолчанию видны в примере.

```json
{
  "jobs_file": "~/.hermes/cron/jobs.json",
  "output": "~/.hermes/data/cron_evals.json",
  "delivery": true,
  "streak_limit": 3,
  "self_monitors": ["8eafdf0f26f9"],
  "checks": [
    {"job": "a372f46fdbd6", "name": "oura snapshot", "max_age_seconds": 97200},
    {"job": "e70f41682aea", "name": "midday digest", "max_age_seconds": 97200, "days": [0, 1, 2, 3, 4]}
  ],
  "state_files": [
    {"name": "watchlist autofetch", "path": "~/.hermes/data/watchlist_state.json",
     "key": "last_check", "max_age_seconds": 12600}
  ]
}
```

| Поле | Смысл |
| --- | --- |
| `checks[].job` | id задачи, как он записан в файле расписаний. Обязательное. |
| `checks[].name` | Человеческое имя для сообщения; иначе берётся имя самой задачи. |
| `checks[].max_age_seconds` | Какой разрыв ещё считается нормой. По умолчанию 27 ч. |
| `checks[].days` | Проверять только в эти дни недели — нумерация Python: понедельник 0 … воскресенье 6 (семёрка читается как воскресенье). Имена тоже работают: `["mon","tue"]`. Пусто — каждый день. |
| `checks[].require_status` | Строка статуса, которая считается успехом. По умолчанию `ok`. |
| `self_monitors` | id задач, по которым серия провалов игнорируется: сторож, который сообщает «3 провала подряд» о самом себе, никогда не сбросит серию. |
| `state_files[].key` | Имя поля со временем внутри файла. По умолчанию `last_check`. |
| `streak_limit` | Сколько провалов подряд становится проблемой. По умолчанию 3. |

### Две ошибки, которые загрузчик не пропускает

- конфиг, который не является JSON-объектом;
- проверка без `job`.

В обоих случаях код возврата `2` и сообщение в stderr: конфиг, который молча ничего не
проверяет, хуже конфига, который падает громко.

## Что проверяется и когда

| Вопрос | Когда проверяется |
| --- | --- |
| Задача есть, включена, попадает в своё окно часов | всегда; иначе состояние `skip`, а не `fail` |
| Последний прогон свежий, `last_status = ok` | по каждой настроенной проверке |
| `last_delivery_error` у любой включённой задачи | по всему списку задач |
| `failure_streak >= streak_limit` | всегда, минус `self_monitors` |
| Файлы состояния ещё обновляются | по каждой настроенной записи |

Состояние `skip` несёт причину (`disabled`, `not scheduled today`, `outside its window`). Такие
пропуски никогда не доставляются — они видны только в JSON-отчёте и под `--all`.

## Командная строка

```sh
agent-cron-evals --config evals.json              # только проблемы (это и запускает крон)
agent-cron-evals --config evals.json --all        # все проверки плюс строка сводки
agent-cron-evals --config evals.json --json       # весь отчёт целиком
agent-cron-evals --config evals.json --quiet      # записать отчёт и ничего не печатать
```

Коды возврата: `0` — проверка выполнена (находки это *вывод*, а не статус), `2` — не удалось
прочитать конфиг или файл задач. Это сделано намеренно: у сторожевой задачи, чей код возврата
скачет от находок, планировщик быстро помечает провал и перестаёт её читать.

## Чем это не является

- **Не планировщик.** Никогда не пишет в файл задач, не перевзводит задачи, ничего не чинит.
- **Не модель.** LLM здесь нет вообще: все проверки — арифметика по времени.
- **Не дашборд.** JSON-отчёт существует, чтобы его можно было запросить; интерфейс — сообщение.
- **Не оценка смысла задачи.** Он знает, что задача отработала и доставила; была ли сводка
  *хорошей* — другая задача.
